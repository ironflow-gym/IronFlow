# 2.4.1: Today, scheduling, and explainable progression

Implemented on branch `2.4`, starting at `4f7c962e9d86f08a0090b8c0ed9c052fd0f8e71e`. Application/package metadata and the service-worker cache are aligned to release `2.4.1`. Storage and backup format versions remain unchanged. The branch’s existing GitHub Pages workflow runs development checks before deploying on push.

## Today and navigation

Today is the default screen, including when a recoverable workout exists. Its primary action resumes that workout before offering an explicit scheduled workout, the existing inferred rotation, or routine creation. An explicit rest day replaces the rotation prompt; choosing an unscheduled workout remains available. Manage routines leads to Plan on both desktop and mobile.

The workout card shows exercises, working sets, approximate duration (working sets plus rest and setup), and last performance. Preview permits per-session choices before starting. The supporting summary shows completed sessions against the existing weekly goal and a factual history/strength-trend item. Existing local save and cloud backup status/retry controls remain above the screen. Missed workout bookings remain actionable; nothing moves them automatically.

The calendar shows all seven days on desktop. Mobile uses a horizontally scrollable day selector and appointments for the selected day. It supports multiple bookings per day, routine replacement, moves, explicit rest, skips, removal and weekly repetition. Weekly edits and removal offer this occurrence or this and future occurrences. Starting another workout while one is unfinished resumes the existing workout instead of replacing it.

## Scheduling records and completion identity

`ironflow_schedule` contains:

- `appointments`: individual appointments or weekly series, identified by stable IDs and local `YYYY-MM-DD` dates, with optional inclusive `until` boundaries.
- `exceptions`: occurrence-specific moves, replacements, skipped/removed/completed status. An occurrence ID combines the series ID and its original calendar date; moving it does not change its identity.
- `completions`: session IDs, actual completion dates and historical names, optional template IDs and exact fulfilled appointment IDs.

A future-series edit splits the series. Past and completed occurrence identities remain intact. Already completed occurrences are not recreated in the replacement series. Skipped and removed occurrences remain dismissed.

Appointment references use routine IDs. A renamed routine supplies its new name to future bookings; a missing routine shows Routine unavailable and replacement/removal actions. A started workout retains its name, exercise and set snapshot. New historical set logs include session, routine and appointment IDs; names remain snapshots. Completion updates history, schedule, and draft deletion in the existing atomic autosave transaction. An unscheduled workout never fulfills a booking through a name/date guess.

The calendar uses local date parts and calendar arithmetic, not UTC serialization. The week begins Monday. Browser tests exercise Australia/Brisbane; date arithmetic tests include month/year and daylight-saving boundaries.

Schedule data participates in autosave, the existing Drive mirror (which includes application records), and JSON vault exports. Older backups without this key load an empty calendar. JSON restore still uses the existing atomic replacement and device-settings preservation behavior.

Older history has no session IDs. For display and weekly counts, it is grouped by date and recorded routine name; multiple legacy sessions with the same name on the same day cannot be distinguished. New sessions use explicit IDs, including multiple sessions on one day. This grouping is never used to fulfill appointments.

## Existing progression, now explained

The weight calculation was extracted from App into `src/progression.ts`. Its existing priority remains:

1. Most recent matching exercise/routine history uses the existing double-progression function.
2. Other history for that exercise either uses that function or projects the recorded weight to a sufficiently different rep range through estimated 1RM.
3. Percentage guidance in the routine rationale may use related category history.
4. A recent routine/AI starting weight may be used within the existing category plausibility bounds.
5. Related exercise history may provide a rep-range-adjusted estimate, with the existing dumbbell per-hand/total conversion.
6. Routine starting weight, or the existing fallback, is used when history is insufficient.

Double progression is unchanged: reaching the upper rep target increases weight and returns to the lower target; below-range performance holds weight at the lower rep target; otherwise it holds weight and adds one rep. Existing rounding, increments and history filtering remain. There is no new requirement for two sessions or every set to reach the upper target. Mixed-unit historical weights are now normalized before comparison, rather than treating a pounds value as kilograms or vice versa.

Workout preview and active strength exercises distinguish same-exercise history, related estimates, and routine starting values. They show the last matching performance, the calculation reason, units, and dumbbell per-hand convention. Use suggestion, Keep previous values, and Enter my own only update unfinished working sets in the current session. Completed sets, warmups, deloads and future routine defaults are preserved. Changing defaults requires editing the routine explicitly. Cardio does not display strength-progression controls.

## Validation and limits

Run from `/workspace/IronFlow` using Node.js 24:

```sh
npm ci
npm test
npm run build
npm run test:e2e
```

The browser suite uses `/usr/bin/chromium` when available, otherwise `CHROMIUM_EXECUTABLE_PATH` or Playwright Chromium. It owns port 5174. Development uses `npm run dev -- --host 127.0.0.1 --port 5173 --strictPort`.

Focused tests cover scheduling priority, exact versus unscheduled completion, missed appointments, occurrence and future edits, moved weekly occurrences, renamed/deleted routines, old-backup defaults, local dates, unit conversion, explicit choices and preservation of existing double-progression results. Browser tests cover Today, preview and active choices, calendar edits/recurrence/completion, historical names after routine edits, mobile overflow, JSON compatibility, offline saves, retry, and mocked Drive upload of scheduling data, alongside the original workflows.

Service workers are blocked in browser tests, and Drive is mocked. These checks demonstrate local features while an already-loaded app is offline; they do not validate fresh offline PWA startup or live AI/Drive services. Existing build warnings concern bundle size and mixed imports of ExerciseLibrary. The optional lint script still lacks a declared ESLint dependency/configuration.
