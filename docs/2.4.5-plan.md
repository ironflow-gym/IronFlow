# 2.4.5 — Food accuracy, logging and review

Implemented locally on branch `2.4`, based on pushed commit f54c32529cc58781270aa273fa1e628e0e48d085. No push or deployment is authorised.

## User decisions

The user explicitly approved all three: require confirmation of unknown pantry nutrition bases; use Food's existing detailed targets throughout Food and Nutrition Stats; require missing barcode nutrients to be completed before logging. No legacy basis is inferred from a serving description.

## Accuracy and compatibility

- Food definitions optionally store nutritionBasis (`100g`, `100ml`, `serving`), nutritionSource, and missingNutrients. The optional fields keep older backups readable. Existing unknown definitions are retained and require a one-time explicit review before logging.
- Per-serving values use serving counts. Per-100g/100ml values use grams/millilitres respectively. No gram/volume conversion or density is invented. 120 kcal per serving remains 120 kcal when one 30g serving is logged.
- Changing a basis does not convert stored numbers: the editor tells the user to enter the values printed for the chosen basis. Historical logs and saved meal nutrition snapshots are never rewritten.
- Open Food Facts lookup and product search use one parser: missing/invalid fields are marked unknown; true zeros remain zero. API `_100g` naming alone does not prove grams versus millilitres; users confirm the label basis. Label/page AI extraction omits missing nutrients instead of substituting zero; users review all imports. Known AFCD results are explicitly per 100g.
- Food and Stats share the existing Food target formula, including user multipliers, protein preference, biometrics and units. No new progression/target rules were introduced.
- Macro statistics use seven local calendar dates ending today, exclude future entries, average only logged days, and disclose logged-day coverage and partial entries. Tooltip percentages remain truthful above the chart's visual cap.

## Entry workflows

- Direct manual logging without AI/network, with date, amount description and non-negative numeric validation. All historical entries support date/total correction and explicit deletion confirmation.
- Pantry has Log actions and shared App state. New items, barcode assignments and corrections are immediately available in Food. All pantry edits participate in the existing atomic autosave and backup/retry handling.
- Barcode and pantry logging review explicit quantities and dates before adding. New barcode products are saved to pantry only via an explicit checkbox. Legacy basis/missing-value review updates only the definition.
- AI descriptions prepare a review of every parsed food. Matching one pantry item cannot discard the rest. Users can edit estimates, choose pantry definitions and quantities, remove individual entries, or cancel the batch. Unknown pantry definitions can be reviewed inside the batch without losing other edits. Proposed profile changes are displayed and default off until explicitly checked.
- AI confirmation appends to current application state, preserving manual entries added while requests were pending. Cancelling review keeps the description. Newly generated food is never automatically logged or saved to pantry.
- Saved/repeated meals retain optional provenance and recorded amount descriptions; changed quantities describe multiples without falsely retaining an unscaled amount label.

## Interface and reliability

- Shared native Modal for pantry, definition editor, manual entry/correction, barcode scanner, label camera, quantity confirmation and batch review. Focus trapping/restoration, Escape, readable labels, and fixed Save/Add/error footers.
- Pantry Log is primary; Edit/Delete are under Options; import/search/label scan are under Find or import foods. Legacy jargon and hover-only delete controls were removed.
- Barcode manual entry preserves leading zeros. Camera tracks and ZXing controls are stopped on exit. Fresh scanner/food requests do not require an AI key; network-dependent methods report failures without silently replacing entries.
- App owns pantry state; it is included in local snapshots, JSON exports/restores and Drive backup payloads with no new storage key. Missing nutrient placeholders remain explicitly flagged, never treated as loggable zeros.
- Version, metadata and service-worker cache advance to 2.4.5.

## Follow-up interface cleanup

The user approved the interface review and explicitly chose discard confirmation rather than retained/reopenable drafts.

- New barcode products use Review product details → Continue to amount, accurately reflecting that pantry saving is an optional later checkbox. Actual pantry creation/editing retains Save pantry food. Quantity dialogs use Log food for both paths.
- AI review defaults to compact food summaries, with editable fields under Edit food. The fixed footer displays the complete batch calorie total and Add N foods. Pantry suggestions are relevant to each original food; Choose pantry food opens a searchable picker for the full collection. Choosing a suggestion/pantry item remains explicit.
- The active food workflow displays the existing durable saving/failure state with Retry save, including pantry, batch, saved-meal, entry, and quantity dialogs. Messages do not imply a successful disk write while failures are pending.
- Shared field validation names the affected food in batch/amount errors, marks fields with aria-invalid and a visible border, associates the footer error with the field, opens collapsed adjustments, and focuses the affected field. Manual, pantry, batch, repeat and saved-meal editors use this behaviour.
- Changed food forms show Keep editing / Discard changes on close or Escape. Untouched forms close directly. Unconfirmed AI review results are treated as pending content and require confirmation to discard; cancelling leaves the original description. Successful submit bypasses discard confirmation. Drafts are not persisted for reopening or across reloads.
- Labels use Values on the label, Check food details, and Calorie adjustment. Target adjustment previews current → proposed kcal and requires Apply. Nutrition chart labels are larger/brighter, figures use two columns on mobile, and solid/dashed series have a written legend.
- Browser additions cover compact mobile totals/actions, searchable pantry choice, field focus/errors, discard/Keep editing with focus return, in-dialog failed save retry, barcode Continue semantics, and target preview/apply. Earlier correctness and backup tests remain included.
