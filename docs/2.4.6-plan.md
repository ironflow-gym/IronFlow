# 2.4.6 — Simple, safer restoration

Release 2.4.6 on branch `2.4`. The user authorised committing and pushing this release. Pushed as adefc74f150ec3185a9517fd139d4a77c64108eb. The user confirmed successful deployment and functioning on 26 October 2026 (Australia/Brisbane).

## Agreed scope

Normal automatic Drive backups and JSON backup creation keep their existing formats and contents. Restoring remains a whole-device replacement; partial restore and merging are deferred. After restore or undo, local saving continues and automatic Drive uploads stay paused until the explicit **Back up restored data** action.

## Restore flow

- Vault Backup opens the shared native **Backup and restore** dialog. Download JSON backup, Restore from File and Restore from Google Drive are the main actions. File and cloud sources share one review and confirmation flow.
- Before confirmation, structural validation checks recognised collections and nested workout, meal and calendar records. Unrelated/malformed files cannot replace data. Older raw JSON files and the existing Drive envelope remain supported without inferring missing categories.
- Review shows source/date when recorded, current versus backup counts, an explicit replacement/missing-category warning, unfinished-workout warning and recovery/pause explanation. Other contents are available under one disclosure. Workout counts are explicitly labelled recorded sets, not fabricated session totals. JSON files without embedded timestamps do not claim their filesystem modified date is the backup date.
- Device settings and connection are retained, matching previous restore behaviour. Missing categories are cleared. Imported records retain their IDs, historical names, optional food metadata and relationships.
- Unsaved/failed local writes block restoration with the existing Retry save action inside the dialog. No failed edits are silently discarded. Cancel changes nothing.

## Recovery and Drive protection

- One IndexedDB transaction captures the complete previous device state, replaces public data, and records a durable Drive pause. If recovery creation or replacement fails, the entire transaction aborts; original data and any previous recovery copy remain intact.
- The recovery snapshot includes unfinished workouts and device-local pending records. It is internal metadata: JSON exports and Drive uploads never include it or the durable pause.
- Recovery remains available after reload/reopening through **Review undo restore**. Undo has the same comparison/replacement warning, replaces any subsequent changes, consumes the recovery copy once, and leaves Drive paused. A later restore replaces the previous recovery copy. Clearing browser data removes local recovery.
- App autosave stays blocked between restore commit and the explicit Continue reload, preventing old React state from replacing restored records. Errors before commit leave the review available for retry.
- Restore waits for an already-running upload before replacing records and locks the queue during restoration. The durable pause is respected after reconnect, reload, new local saves, normal backup requests and OAuth returns.
- Paused status remains visible in the main save/backup status, Backup and restore and connected Settings. Explicit **Back up restored data** resumes normal automatic backup processing; reauthorisation/connect is requested if needed. Offline or failed uploads remain pending using existing queue behaviour.
- Browsing Drive backups is read-only; retention pruning continues after normal uploads rather than deleting files while selecting a restore source.

## Interface

Uses the existing shared native Modal, labelled headings, focus management, Escape/cancel, readable text, 44px controls and a fixed action/error footer. One focused review replaces the former dense jargon-heavy manifest. Busy/committed restore cannot be dismissed into stale application state; Continue reloads after success. No new dashboard or configuration screen.
